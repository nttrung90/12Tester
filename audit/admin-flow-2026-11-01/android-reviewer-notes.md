# Findings to recheck after Android implementation finishes

## Dialog state
Intermediate AdminUsersScreen code uses primitive rememberSaveable IDs but clears them unconditionally in LaunchedEffect(currentAdminId). That effect runs again on Activity recreation, immediately discarding restored dialog/ID. It also cannot detect same UID with new SessionCacheManager generation. Ensure final code preserves selection/draft on same-session recreation and clears them for changed UID OR generation, including private/broadcast notification drafts and config dialog success signals. Consider saved owner identity alongside IDs plus a uiState session identity; do not blindly clear on initial composition. RememberSaveable inputs alone may restore values from previous inputs after process recreation unless ownership is encoded/validated. Confirm AdminReports screen follows same contract.

## Campaign action ownership
Intermediate CampaignDetailViewModel uses one AtomicBoolean isAdminActionInProgress and checks identity before publishing, but after auth/generation change it leaves isActionLoading=true because finally only clears if identity matches. Existing auth observer does not reset the admin action. The old boolean blocks a new session until old network completes; naïvely resetting it on auth switch would let the old finally clear the new action's gate. Use owned serial/token, reset the OLD session's admin loading on session change, and allow new session action without old completion clearing the new flags. Cancellation/finally must release only its own admission. Add delayed old action -> switch session -> start new action -> finish old while new pending test, including delete callback guard. Keep scope limited to admin methods and associated observer/reset.

## Repository admission atomicity
Intermediate AppConfigRepository increments mutationSeq then inFlightMutations in separate atomic operations, while readers capture the same fields separately. A reader can start in between, record the new generation while no mutation is in flight yet, then publish stale data after successful save (same generation). Register mutations and capture read tokens under the SAME cacheLock used by cache publication; also unregister mutation under that lock, or use an equivalent atomic snapshot. Keep public cache global and cancellation semantics. Sequence barriers should guard memory + disk publication together.
